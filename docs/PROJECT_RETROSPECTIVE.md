# LG Aimers 9기 프로젝트 회고

> 2026년 8월 11일부터 9월 2일까지, 다음 시즌을 제대로 예측하는 검증 체계부터
> 만들고 전처리와 모델을 단계적으로 좁혀 간 23일간의 기록이다.

## 한눈에 보는 결론

이 프로젝트의 목표는 야구 투구 직전의 정보로 `control_success=1`, 즉 제구 성공
확률을 예측하는 것이었다. 가장 높은 규칙 준수 Public 점수는 Tree Expert E2의
`977.3809532715`다. 첫 CatBoost 제출 `828.9963889533`보다 약 148.38점, 첫 TabM
제출 `872.3920184667`보다 약 104.99점 높다.

점수보다 오래 남은 성과는 실험을 판단하는 방식이다. 과거 시즌으로 학습하고 다음
시즌을 예측하는 시간 전이 검증을 공통 시험으로 삼았고, 실행 오류와 성능 기각을
구분했다. 평가 데이터의 다른 행을 참조하지 않는 규칙도 모델 성능과 별도의 합격
조건으로 만들었다.

마지막 E3는 1,000점에 도전한 후보였지만 점수를 얻은 실험이 아니다. **성능을
판정할 수 없었던 실행 실패**다. Kaggle에서 `33,677.4초` 동안 OOF 작업 63개 중
53개를 마친 뒤 메모리 부족으로 종료됐다. 이 결과로 모델 성능을 좋거나 나쁘다고
주장하지 않는다.

## 이 문서를 읽는 방법

본문에서는 아래 표시를 사용한다.

- **확인된 사실**: 실행 산출물, 작은 evidence, 해시 또는 Git 기록으로 확인한 내용
- **해석**: 확인된 결과가 다음 판단에 어떤 영향을 줬는지 설명한 내용
- **한계**: 현재 자료만으로 확인할 수 없거나 직접 비교할 수 없는 내용

정확한 실험 수치와 판정은 [실험 장부](../reports/EXPERIMENT_LEDGER.md), 기계 판독
원본은 [experiment registry](../reports/experiment_registry.json)를 기준으로 한다.
이 문서는 그 기록을 복사한 두 번째 장부가 아니라, 왜 그런 선택을 했는지 설명하는
회고다.

## 1. 어떤 문제를 풀었나

모델의 입력은 투구 직전에 알 수 있는 선수와 경기 상황 정보이고, 출력은 제구에
성공할 확률이다. 정답을 0 또는 1로만 맞히는 분류와 달리, 확률 예측에서는 확신의
크기도 맞아야 한다.

이를 재는 지표가 **Brier Score**다. 예측 확률과 실제 정답의 차이를 제곱해 평균하며
낮을수록 좋다. 예를 들어 실패한 투구를 90% 성공한다고 예측하면, 60%라고 예측했을
때보다 더 큰 벌점을 받는다. DACON Public 점수는 Brier가 개선될수록 높아지는 별도
점수다. 따라서 로컬 Brier와 Public 점수는 같은 표에서 순위를 만들지 않았다.

이 대회에는 성능 외에 중요한 제약도 있었다. 평가 데이터의 각 행은 다른 평가 행과
독립적으로 예측해야 했다. 같은 평가 파일에 들어 있는 다른 투구의 평균, 빈도, 순위,
누적값을 사용하면 예측 시점에 알 수 없는 정보를 간접적으로 이용할 수 있기 때문이다.

## 2. 대회 규칙을 실험 절차로 바꾼 방법

**확인된 사실**

- 사용 데이터는 공식 학습 데이터와 공식 TrackMan 데이터로 제한했다.
- 평가 범위는 `current_row_only`, 즉 현재 행 하나만 보도록 고정했다.
- 행 순서 반전, 무작위 섞기, 배치 크기 변경, 한 행 추론으로 예측 불변성을 검사했다.
- 검증 때 사용한 코드, 설정, 전처리와 모델 해시가 달라지면 패키징을 막았다.
- Public 점수를 본 뒤 가중치나 보정 강도를 다시 고르지 않았다.

현재 저장소의 규칙 기준은
[`dacon-236743-2026-08-15`](../competition_rules/policy.json)다. 실험 상태와 제출
조건은 [실험 실행 계약](EXPERIMENT_CONTRACT.md)에 정리돼 있다.

**해석**

규칙 검사는 마지막 제출 직전의 체크리스트가 아니라 모델 선택 과정의 일부였다.
XGBoost 공격적 탐색은 Public `820.9583317093`을 기록했지만 평가 예측 전체의 평균을
이동하는 보정을 사용했다. 현재 규칙과 맞지 않아 역사적 결과로만 남기고 재사용하지
않았다.

**한계**

코드는 데이터 사용과 행 독립성을 검사할 수 있지만 팀 상태, 당일 제출 횟수, 마감과
실제 업로드 파일 선택은 자동으로 확정할 수 없다. 이 항목은 사용자가 제출 직전에
직접 확인했다.

## 3. 데이터와 검증 전략

무작위 분할은 같은 선수와 비슷한 시기의 기록을 학습과 검증에 동시에 섞을 수 있다.
로컬 점수가 좋아도 다음 시즌을 예측하는 상황과 달라질 위험이 있었다. 그래서 다음
세 번의 시간 이동을 공통 시험으로 사용했다.

```text
2021년까지 학습 → 2022년 예측
2022년까지 학습 → 2023년 예측
2023년까지 학습 → 2024년 예측
```

각 검증 행은 그 행의 정답을 학습하지 않은 모델이 예측했다. 이런 예측을 **OOF
(out-of-fold) 예측**이라고 한다. R9 CatBoost anchor는 세 전이에서 746,504개 OOF
행을 만들었고 Brier `0.24825099524638927`을 기록했다. 이후 같은 행과 같은 방식으로
검증한 후보만 이 기준과 직접 비교했다.

모든 실험에 똑같은 검증 방법을 쓰지는 못했다. 전처리 탐색은 계산량을 줄인 예비
검증인 proxy와 전체 학습 비교를 함께 사용했고, TabM·CatBoost 혼합은 두 개 시간
fold를 사용했다.
그래서 registry의 `comparison_group`이 다른 Brier는 크기만 보고 우열을 정하지
않는다. 자세한 그룹별 결과는 [실험 증거 재감사](../reports/EXPERIMENT_RESET_AUDIT.md)에
있다.

## 4. 전처리 연구: 많이 넣기보다 하나씩 확인했다

전처리는 모델이 데이터를 읽기 좋은 형태로 바꾸는 과정이다. 정규화나 선수별 평균이
일반적으로 유용하더라도 이 데이터에서 실제로 좋아진다는 보장은 없었다. T4 GPU 2장
예산 안에서 다섯 단계로 범위를 줄였다.

1. TabM, FT-Transformer, TabNet과 CatBoost를 비교했다.
2. 수치 변환과 선수별 평활화를 하나씩 바꿨다.
3. 과거 집계, 결측 표시, ID 빈도와 같은 행의 상호작용을 비교했다.
4. 좋아진 후보를 다른 시간 전이와 CatBoost에서 확인했다.
5. 전체 학습 행으로 기본 전처리와 최종 후보를 다시 비교했다.

**확인된 사실**

- 비교한 딥러닝 모델 중 TabM이 가장 좋았고 TabNet sentinel은 승격 기준을 넘지 못했다.
- Yeo-Johnson 변환과 단독 선수 평활화는 기본 TabM을 이기지 못했다.
- 투수와 타자의 손잡이를 같은 행에서 결합한 `hand_matchup`은 TabM의 두 시간 전이와
  CatBoost에서 같은 개선 방향을 보였다.
- 전체 학습 비교에서 기본 TabM Brier는 `0.2483070113`, `hand_matchup`을 더한
  TabM은 `0.2480974092`였다.
- 최종 TabM 전처리는 `dl_standard + hand_matchup`으로 고정했다.

`hand_matchup`은 평가 데이터 전체에서 만든 통계가 아니다. 현재 행의
`pitcher_hand`와 `batter_hand`만 결합하므로 행 독립성 원칙을 지킨다.

초기 OOV 피처는 학습 데이터에서 상수였지만 검증 데이터에서만 값이 달라졌다. 수치
범주를 숫자 벡터로 바꾸는 embedding 과정에서 overflow와 NaN이 발생해 OOV 열을
제거하고 다시 실행했다. 대체 후보는 정상 완료했지만 성능이 나빠 채택하지 않았다.
오류와 성능 기각을 분리한 첫 사례 중 하나였다.

세부 수치와 산출물 해시는
[전처리 Stage 1~5](rounds/06-budgeted-preprocessing-campaign.md)에서 확인할 수 있다.

## 5. 모델과 앙상블 실험 흐름

### 초기 모델 탐색

첫 CatBoost 제출은 Public `828.9963889533`이었다. FwFM, TabM residual,
calibration과 XGBoost를 넓게 확인했지만 한 시즌만 좋아지거나 안정성 조건을 넘지
못한 구성이 많았다. 이때 얻은 결론은 “큰 모델을 더 오래 돌리자”가 아니라 “공정한
검증에서 반복되는 신호를 먼저 찾자”였다.

### 첫 TabM 제출

확정 전처리와 TabM P2를 전체 데이터로 3 epoch 학습해 Public
`872.3920184667`을 기록했다. 3 epoch는 실행 시간이 부족해서 임의로 멈춘 값이
아니다. 이전 검증에서 최대 43 epoch까지 확인했지만, 학습 중 저장한 최적 모델 상태인
checkpoint가 2~3 epoch에 형성됐다. 학습 난수의 출발값인 seed를 여러 개 평균한
결과도 단일 seed보다 나빠 같은 모델을 오래 학습하거나 seed만 늘리는 방향을 닫았다.

### Tree Expert E2

E2의 **anchor**, 즉 출발점은 TabM 예측이 아니었다. 과거 학습 데이터에서 투수의
통산·시즌·최근 성공률을 계산하고 표본 수에 따라 전체 평균 쪽으로 평활화한 확률이었다.
CatBoost는 정답 전체가 아니라 이 확률이 남긴 오차만 학습했다. 이를 **residual
correction**, 잔차 보정이라고 한다. TabM은 E2의 개선을 판단하기 위한 비교 기준이었다.

seed 42, 2026, 3407의 세 모델을 평균했고 세 시간 fold에서 모두 개선됐다. weighted
Brier 개선은 `0.0008375137`, 가장 약한 fold의 개선도 `0.0003439904`였다.
245,789개 행의 독립성 감사에서 최대 예측 차이는 `0`이었다. 승인 후 제출해 프로젝트
최고 Public `977.3809532715`를 기록했다.

### E2 이후

최근 시즌과 과거 시즌을 나눈 T3, 계층 잔차, 실패 유형 전문가, XGBoost·LightGBM
잔차와 TrackMan exact-match teacher를 차례로 확인했다. 일부는 평균적으로 조금
좋아졌지만 최악 시즌, 최소 개선량, 배포 정렬 또는 기존 E2와 다른 오차를 만드는지
검사하는 기준에서 탈락했다.

외부 1130점대 사례는 시즌 정보, 정규 시즌 `R`과 별도 경기 유형 `F`의 전문가,
다중 seed와 이종 트리라는 연구 가설을 얻는 데만 사용했다. 출처가 증명되지 않은
모델이나 학습 통계를 우리 제출물로 가져오지 않았다.

## 6. 후보를 채택하거나 기각한 기준

실험 상태는 다음과 같이 구분했다.

| 상태 | 뜻 |
|---|---|
| `accepted` | 해당 실험에 미리 정한 수용 기준을 통과함. 제출 자격은 별도 확인 |
| `public_scored` | 실제 제출 점수가 확인됨 |
| `rejected` | 실행은 유효하지만 사전에 정한 성능 기준을 통과하지 못함 |
| `failed` | 환경, 메모리, 코드나 산출물 문제로 성능 판정을 끝내지 못함 |
| `diagnostic` | 모델을 학습하기 전에 데이터나 가설의 적격성을 확인함 |

증거 신뢰도도 세 단계로 기록했다.

| 등급 | 기준 |
|---|---|
| A | 원본 review·handoff·delivery 번들을 현재 코드로 검증함 |
| B | 저장소에 acceptance·rejection evidence 또는 산출물 해시가 있음 |
| C | 실행 로그나 대화 기록만 남아 있음 |

등급 C는 과거 흐름을 이해하는 참고 자료로 남기지만 새 후보 승인이나 제출 패키징의
단독 근거로 사용하지 않는다.

### 같은 검증 그룹 안에서 내린 주요 판단

| 비교 범위 | 후보 | 판정 근거 |
|---|---|---|
| R9 시간 전이 3-fold | R9 anchor | 공통 비교 기준으로 채택 |
| R9 시간 전이 3-fold | FwFM·고정 F blend | 평균 이득과 별개로 특정 fold가 악화돼 기각 |
| TabM 시간 전이 2-fold | seed 평균 | 단일 seed 3407보다 Brier가 `0.000318` 이상 악화돼 기각 |
| E2 시간 전이 3-fold | Tree Expert E2 | 세 fold와 행 독립성 기준을 통과해 채택·제출 |
| E2 시간 전이 3-fold | T3 | weighted gain이 음수이고 두 fold가 악화돼 기각 |
| E2 시간 전이 3-fold | 계층 잔차 | 작은 평균 이득은 있었지만 최악 fold와 seed 기준 실패 |
| E2 시간 전이 3-fold | 이종 트리 S3 | 개선량이 기준보다 작고 E2와 오차 상관이 `0.998` 이상이라 기각 |
| E2 시간 전이 3-fold | profile P-only | 세 fold 방향은 양수였지만 최소 gain 기준의 약 40.5%에 그쳐 기각 |
| E2 시간 전이 3-fold | E3 | 메모리 부족으로 최종 판정에 도달하지 못해 `failed` |

이 표는 판정 흐름을 요약한다. 전체 수치와 `repeat_policy`는
[실험 장부](../reports/EXPERIMENT_LEDGER.md)와
[experiment registry](../reports/experiment_registry.json)를 따른다.

계보로 해석하지 않는다. 초기 CatBoost와 FwFM은 원본 제출 해시가 남아 있지 않은
증거 등급 C다.

**한계**

Public 점수와 로컬 Brier는 다른 척도다. 제출 횟수도 적기 때문에 둘 사이의 환산식을
만들거나 Public 점수로 사후 가중치를 최적화하지 않았다. 우리 프로젝트의 최고 확인
점수는 `977.3809532715`이며 1,000점을 넘었다고 표현하지 않는다.

## 8. 운영상 실패와 기술적 교훈

### 재개 가능한 실행은 편의 기능이 아니었다

Kaggle과 Colab의 세션 제한 안에서 긴 학습을 이어 가려면 checkpoint, resume과 결과
번들이 필요했다. 다만 복구 파일이 많아질수록 어떤 파일이 최신인지 판단하기 어려워지고
업로드와 압축 해제에도 시간이 들었다. 이후 실행에서는 manifest와 SHA-256으로 입력을
식별하고 최신 resume 하나만 전달하는 방향으로 구조를 바꿨다.

### 검증 통과와 배포 가능성은 다르다

TabM 70%와 CatBoost 30%의 OOF 혼합은 두 fold에서 좋아졌다. 하지만 제출 때 저장할
수 있는 고정 트리 수로 다시 맞추자 모든 fold를 통과한 설정이 없었다. 좋은 OOF 숫자와
재현 가능한 모델 상태가 일치하지 않으면 제출하지 않는다는 기준을 세웠다.

### E3는 성능이 아니라 자원 계획에서 실패했다

E3는 E2 anchor에 전체·최근·R/F 성공 전문가와 `middle`, `wild`, `reverse` 실패
전문가를 붙인 공격적인 후보였다. Kaggle T4×2에서 63개 OOF 작업 중 53개를 완료한 뒤
`33,677.4초` 시점에 메모리 부족(OOM, out of memory)으로 종료됐다.

decision, 전체 학습과 행 독립성 감사를 시작하지 못했으므로 제출 가능 상태가 아니었다.
부분 Brier를 근거로 기각하거나 채택하지 않았고, registry에는 `failed`, 실패 분류는
`runtime`으로 기록했다. 세부 자원 실패 분류는 `resource_memory`다.

다음 대회에서는 가장 큰 실험부터 시작하지 않는다. 대표 작업 하나로 시간과 최대 메모리
사용량(peak RAM)을 재고 전체 작업 수와 동시 실행 수를 계산한다. 실행 제한의 70~80%
안에 decision과 audit까지 끝나지 않으면 작업 수나 모델 수명을 줄인 뒤 본 실행을
시작한다.

## 9. 23일간의 회고

### 잘한 점

- 모델보다 검증 방식을 먼저 고정했다.
- 평균 점수가 좋아도 한 시즌이 나빠지면 원인을 확인했다.
- 실행 실패와 성능 기각을 다른 상태로 기록했다.
- 규칙 검사를 제출 직전이 아니라 실험 계약과 테스트에 넣었다.
- 외부 고득점 사례에서 아이디어는 얻되 출처가 불명확한 산출물은 가져오지 않았다.
- 대용량 모델 대신 작은 evidence와 해시를 Git에 남겼다.

### 아쉬운 점

- 초반에는 실험 코드와 Colab·Kaggle 전달 구조가 자주 바뀌어 복구 비용이 컸다.
- 장시간 실행의 peak RAM과 총 작업 시간을 파일럿에서 충분히 재지 않았다.
- 실험 이름과 중간 ZIP이 많아 팀원이 전체 흐름을 이해하기 어려웠다.
- Temporal T1·T2A·T2B·T2C, Tree Expert RF와 S4는 최종 원본 번들을 현재 저장소에서
  다시 확인하지 못했다. 결과를 추정하지 않고 증거 공백으로 남겼다.
- 일부 초기 제출은 로그만 남아 제출 해시와 전체 계보를 복원할 수 없다.

### 내가 이해한 것

좋은 모델은 이름이나 최신성만으로 결정되지 않는다. 이 프로젝트에서는 검증된 anchor,
범주형 상호작용에 강한 CatBoost와 작은 잔차 보정의 조합이 가장 큰 확인 개선을 만들었다.
반대로 모델 계열이 달라도 같은 피처와 같은 오차를 학습하면 앙상블의 이득이 작았다.

또한 OOF에서 좋아진 모델이 곧 제출 가능한 모델은 아니다. 같은 전처리, 트리 상태,
규칙과 추론 방식으로 재현돼야 비로소 후보가 된다. 실행이 끝나지 않았다면 일부 숫자가
좋아 보여도 성능 근거가 아니다.

## 10. 사용자와 Codex의 역할

### 사용자가 직접 결정하고 실행한 일

- 실험 범위, 우선순위와 GPU 예산 승인
- Kaggle·Colab 전체 데이터 학습과 장시간 실행
- 로그와 결과 ZIP 확인 및 공유
- 후보 채택 여부와 실제 DACON 제출 결정
- Public 점수 확인과 다음 방향 승인

### Codex가 지원한 일

- 실험 코드와 한 셀 실행 코드 작성
- checkpoint, resume, handoff와 manifest 구조 설계
- 규칙 검사, 행 독립성 검사와 산출물 해시 검증
- 작은 합성 데이터와 fixture 기반 테스트 작성
- 결과 번들 분석과 실험 기록 정리

AI가 코드 작성을 도왔다는 사실과 프로젝트를 이해하고 판단했다는 사실은 모순되지
않는다. 사용자는 가설과 위험, 실행 결과와 제출 여부를 검토했다. Codex는 그 판단을
재현 가능한 코드와 증거 구조로 옮기는 역할을 맡았다. 전체 데이터 학습과 실제 제출을
Codex가 대신 실행한 것으로 표현하지 않는다.

## 11. 다음 대회에서 적용할 운영 방식

1. **규칙과 평가 방식을 먼저 고정한다.** 공식 공지의 버전과 날짜를 정책 파일에 남긴다.
2. **비교 기준을 먼저 만든다.** 배포 상황과 닮은 시간 전이 OOF를 champion으로 고정한다.
3. **실험 카드를 실행 전에 작성한다.** 가설, 비교 그룹, fold, 최소 개선량과 중단 조건을
   적는다.
4. **저비용 적격성 검사를 먼저 한다.** 데이터 coverage와 라벨 품질이 부족하면 모델을
   학습하지 않는다.
5. **대표 작업으로 자원을 측정한다.** 시간, CPU·GPU 메모리와 산출물 크기로 전체 예산을
   계산한다.
6. **단계마다 판정한다.** screening을 통과한 후보만 추가 seed와 전체 학습으로 보낸다.
7. **최신 resume 하나만 보존한다.** 이전 resume은 원격 보관하되 다음 입력 후보에서
   제외한다.
8. **검증과 배포 상태를 맞춘다.** 저장 모델, 전처리와 추론 코드가 OOF 상태와 같아야 한다.
9. **실패와 기각을 즉시 기록한다.** 원인, 다음 판단과 반복 정책까지 남긴다.
10. **문서를 실험과 함께 갱신한다.** registry를 기준으로 장부와 자동 감사의 동기화를
    검사한다.
