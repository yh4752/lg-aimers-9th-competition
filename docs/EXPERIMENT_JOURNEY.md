# 실험 여정: 무엇을 시도했고 왜 방향을 바꿨나

이 문서는 모델 이름을 나열한 실행 로그가 아니다. 어느 시점에 어떤 문제를 봤고,
그 문제를 풀기 위해 무엇을 실험했으며, 결과가 다음 선택을 어떻게 바꿨는지 설명한다.
정확한 수치와 산출물 식별값은 [실험 장부](../reports/EXPERIMENT_LEDGER.md)를 기준으로
한다.

## 먼저 알아둘 말

### Brier Score

비 예보를 떠올리면 쉽다. 비가 올 확률을 90%라고 했는데 비가 오지 않으면, 60%라고
했을 때보다 더 크게 틀린 것이다. Brier Score는 예측 확률과 실제 정답의 차이를
제곱해 평균낸 값이다. **낮을수록 확률을 더 정확하게 말한 모델**이다.

이 대회의 Public 점수는 Brier가 좋아질수록 높아지는 별도 점수다. 따라서 문서에서
`Brier 0.248`은 낮을수록 좋고, `Public 977`은 높을수록 좋다.

### 시간 전이 검증과 OOF

시간 전이 검증은 작년 자료로 공부한 뒤 올해를 맞혀 보는 모의고사다. 예를 들어
2021년까지 학습한 모델로 2022년을 예측한다. 미래 시즌의 정답을 미리 본 모델은 이
시험에 참여할 수 없다.

OOF는 **out-of-fold**의 약자다. 각 행을 예측할 때 그 행의 정답을 학습에서 제외한
모델이 만든 확률을 뜻한다. 여러 모델을 공정하게 섞거나 오차를 분석하려면 이런
예측이 필요하다.

### Anchor와 residual correction

Anchor는 새 모델이 출발할 기준 확률이다. 시험 답을 처음부터 다시 쓰기보다, 이미
작성한 답안에서 반복되는 실수만 고친다고 생각하면 된다. 이때 고칠 부분이 residual,
즉 잔차다. 새 모델이 기존 예측과 정답의 차이를 학습해 작은 폭으로 수정하는 방식이
residual correction이다.

### 앙상블

한 사람의 판단보다 성향이 다른 여러 사람의 판단을 모으면 실수를 줄일 때가 있다.
모델의 예측을 평균하거나 일정 비율로 합치는 것도 같은 원리다. 다만 비슷한 모델만
여럿 모으면 같은 실수를 반복할 수 있어, OOF에서 실제로 보완 관계가 있는지 먼저
확인했다.

## 1. 점수보다 먼저 시험 방식을 고정했다

### 문제 인식

무작위로 학습 자료와 검증 자료를 나누면 같은 선수와 비슷한 시기의 정보가 양쪽에
섞인다. 로컬 점수는 좋아 보여도 다음 시즌을 예측하는 실제 상황과 멀어질 수 있었다.

### 가설과 설계

2021→2022, 2022→2023, 2023→2024의 세 시간 전이를 공통 시험으로 삼았다. 모델과
전처리는 과거 구간에서만 학습하고, 미래 시즌에는 고정된 상태를 적용했다. 이 과정에서
R9 CatBoost anchor의 746,504개 OOF 행과 Brier `0.24825099524638927`을 비교 기반으로
확정했다.

### 판단

이후 실험은 “한 번의 좋은 숫자”보다 여러 시즌에서 같은 방향으로 좋아지는지를 먼저
보게 됐다. 서로 다른 검증 방식에서 나온 Brier를 억지로 한 줄에 세우지 않는 원칙도
이때 정했다.

## 2. 여러 모델을 넓게 보되, 실패한 계열은 닫았다

초기 CatBoost 기준선은 Public `828.9963889533`을 기록했다. 이후 후보는 이 점수만
보고 고르지 않고, 공통 시간 전이 검증에서 먼저 비교했다.

### FwFM과 초기 residual

범주형 상호작용에 강한 FwFM을 단독 모델과 `game_type=F` 전용 혼합으로 시험했다.
일부 전체 Brier는 낮아졌지만 특정 시즌이 나빠졌고, 종료 감사에서도 안정적인 신호를
찾지 못했다. FwFM 계열은 종료했다.

TabM으로 R9의 오차를 바로 보정한 초기 residual 구성도 R9보다 Brier가
`0.0041512419` 악화됐다. 이 결과는 TabM 전체가 나쁘다는 뜻이 아니라, 그 residual
구성 하나를 폐기할 근거였다.

### Calibration과 XGBoost

확률의 세기를 조정하는 calibration은 평균 Brier를 낮췄지만, calibration gap과
시즌별 안정성 기준을 함께 통과하지 못했다. 고정한 세 변형은 기각하고 연구 계열만
열어 뒀다.

XGBoost는 넓은 깊이와 leaf 수, 여러 seed를 비교했다. 공격적 탐색 제출은 Public
`820.9583317093`을 기록했다. 다만 평가 예측의 전체 평균을 이동시키는 보정이 들어가
현재의 평가 행 독립 원칙과 맞지 않았다. 점수와 교훈은 남겼지만 모델과 후처리는
격리하고 다시 쓰지 않았다.

### 다음 단계

모델 용량을 늘리는 것만으로는 부족했다. 어떤 입력 표현이 여러 모델과 시즌에서
재현되는지 전처리부터 다시 확인하기로 했다.

## 3. 전처리 Stage 1~5: 많이 넣기보다 하나씩 확인했다

### 문제 인식

정규화나 선수 통계는 보통 도움이 된다고 알려져 있지만, 이 데이터와 모델에서도
그렇다는 보장은 없었다. 가능한 조합을 전부 돌리면 후보 수와 GPU 시간이 급격히
늘어난다.

### 실험 설계

T4 GPU 2장의 실행 예산 안에서 다섯 단계로 범위를 줄였다.

1. TabM, FT-Transformer, TabNet과 CatBoost를 비교했다.
2. 수치 변환과 선수별 평활화를 하나씩 바꿨다.
3. 과거 집계, 결측 표시, ID 빈도와 같은 행의 상호작용을 비교했다.
4. 좋아진 후보를 다른 시간 전이와 CatBoost에서 다시 확인했다.
5. 전체 학습 행으로 기본 전처리와 최종 후보를 비교했다.

### 확인된 결과

비교한 DL 중 TabM이 가장 좋았고, TabNet sentinel은 승격 기준을 넘지 못했다.
Yeo-Johnson 변환과 단독 평활화는 기본 TabM을 이기지 못했다. 반면 투수와 타자의
손잡이를 같은 행에서 결합한 `hand_matchup`은 TabM의 두 시간 전이와 CatBoost에서
모두 같은 개선 방향을 보였다.

전체 학습 비교에서 기본 TabM의 Brier는 `0.2483070113`, `hand_matchup`을 더한
TabM은 `0.2480974092`였다. 사전에 정한 선수 ID·경기 유형 구간에서도 모두
좋아졌다. 최종 전처리는 `dl_standard + hand_matchup`으로 고정했다.

초기 OOV 피처는 학습 자료에서 상수였고 검증 자료에서만 값이 달라져 수치 embedding
과정에서 overflow와 NaN을 만들었다. OOV 열을 제거한 대체 실험은 정상 종료했지만
성능이 나빠 채택하지 않았다. 오류를 숨기지 않고 피처 정의를 바꾼 사례다.

세부 결과는 [전처리 Stage 1~5](rounds/06-budgeted-preprocessing-campaign.md)에 있다.

## 4. 첫 TabM 제출: 오래 학습하는 것이 답은 아니었다

확정한 전처리와 TabM P2를 전체 자료로 3 epoch 학습해 제출했다. Public 점수는
`872.3920184667`이었다. 3 epoch는 시간이 부족해 임의로 멈춘 값이 아니다. 앞선
검증에서 최대 43 epoch까지 확인했지만 최적 checkpoint가 2~3 epoch에 형성됐다.

따라서 다음 가설을 “epoch를 더 늘리자”로 잡지 않았다. seed 평균, 행 단위 파생변수,
CatBoost와의 보완 관계를 먼저 확인했다. TabM seed 평균은 단일 seed 3407보다
`0.000318` 이상 나빠 기각됐다. 행 단위 파생변수 연구는 실행·복구 구조까지 만들었지만
새 Public 점수로 이어진 승인 결과는 확인되지 않아 성과 수치로 적지 않는다.

첫 제출의 점수 해석과 파일 무결성은 [TabM 첫 공식 제출](rounds/07-tabm-first-submission.md)에
정리했다.

## 5. 혼합 모델: OOF 통과와 배포 가능성은 다른 문제였다

TabM과 CatBoost가 서로 다른 실수를 한다면 두 확률을 섞어 이득을 볼 수 있다고
생각했다. 같은 두 시간 전이 OOF에서 TabM 70%, CatBoost 30%가 weighted Brier를
`0.2494662366`에서 `0.2492874755`로 낮췄다. 두 시즌 모두 좋아졌고 이 단계의 고정
혼합 기준은 통과했다.

하지만 이 결과를 곧바로 제출하지 않았다. 실제 배포 때 저장할 CatBoost의 고정 트리
수와 동일한 조건으로 4, 32, 64, 128, 192, 296, 400개 트리를 다시 비교했다. 가장
작은 4개 트리는 전체로는 `0.0000320407` 좋아졌지만 2023→2024가
`0.0001464537` 나빠졌다. 나머지 설정도 모든 시간 구간을 통과하지 못했다.

결론은 “앙상블이 무의미하다”가 아니다. **OOF에서 좋아 보인 가중치와 실제로 재현할
수 있는 모델 상태가 정확히 맞아야 한다**는 교훈을 얻었다. 배포 정렬이 끝나지 않은
혼합은 제출물로 만들지 않았다.

## 6. Tree Expert E2: 기존 확률의 오차만 고쳤다

### 문제 인식

TabM 단일 모델은 872점까지 올랐지만, 범주형 상호작용과 시즌별 반복 오차를 충분히
잡지 못했다. 모든 것을 새로 예측하는 큰 모델보다 기존 확률의 실수에 집중할 필요가
있었다.

### 설계

기존 예측을 anchor로 고정하고 CatBoost가 잔차를 학습하게 했다. seed 42, 2026,
3407의 세 모델을 평균했다. 후보 선택은 세 시간 전이에서 했고, 245,789개 행을
대상으로 순서 반전, 무작위 섞기, 재배치, 한 행 추론도 확인했다.

### 결과와 판단

weighted Brier 개선은 `0.0008375137`, 가장 약한 시즌의 개선도 `0.0003439904`,
bootstrap 95% 하한은 `0.0006692336`이었다. 행 배치 방식을 바꿨을 때 최대 예측
차이는 `0`이었다. 후보를 승인해 제출했고 Public `977.3809532715`를 기록했다.

이 결과는 첫 TabM보다 약 104.99점 높았다. 최신 DL을 더 크게 만드는 것보다, 검증된
anchor와 범주형 트리 모델의 잔차 보정을 결합한 방식이 이 단계에서는 더 잘 맞았다.

## 7. 977점 이후: 좋아 보이는 아이디어를 그대로 믿지 않았다

### 최근 시즌과 과거 시즌을 나눈 T3

직전 시즌 전용 모델과 오래된 시즌을 감쇠한 다중 시즌 모델을 따로 학습하고 비율을
바꿨다. 선택된 구조는 감쇠 `0.75`, 최근 모델 비중 `0.70`이었지만 weighted gain이
`-0.0000505772`였다. 2022→2023만 좋아졌고 나머지 두 전이는 나빠 구조 게이트에서
탈락했다.

### 계층 보정

선수와 경기 문맥을 계층적으로 더 반영한 잔차 후보 C1·C2를 시험했다. C1은 작은
평균 개선이 있었지만 2021→2022와 seed 일관성 기준을 통과하지 못했다. C2도 최소
시즌 개선과 구간 회귀 기준을 넘지 못했다. 새 후보 없이 E2에 해당하는 C0로
돌아갔다.

### 실패 유형 전문가

고득점 외부 사례에서 `middle`, `reverse`, `other_failure` 전문가 아이디어를 얻었다.
모델부터 만들지 않고, 공식 학습 자료만으로 이 라벨을 일관되게 복원할 수 있는지 먼저
감사했다. 2021~2024 네 cutoff에서 라벨 coverage는 약 96.4~96.5%였고,
`middle`과 `reverse`가 약 7.2~7.4% 겹쳤다. 사전 기준을 통과한 유형이 없어 세
전문가를 모두 학습 부적합으로 판정했다.

이 실험들은 Public 점수를 만들지 않았다. 대신 시간 가중, 계층 보정, 실패 유형을
현재 정의 그대로 반복할 이유가 없다는 정보를 남겼다.

## 8. 이종 트리 S3: 모델 이름이 달라도 오차는 비슷했다

1130점대 외부 제출 구조를 검토하면서 고득점의 중심이 단일 대형 DL이 아니라 시즌별
통계, 상황별 전문가, 여러 seed와 이종 트리의 결합이라는 가설을 얻었다. 외부 모델과
코드를 가져오지 않고, 우리 OOF 계보와 규칙 계약 안에서 재검증하기로 했다.

S3는 E2 anchor를 고정하고 XGBoost와 LightGBM이 남은 오차를 각각 학습했다. 보정
폭은 5%, 10%, 15%만 비교했고, 2022·2023 OOF에서 구조를 고른 뒤 2024를 한 번만
확인했다. 평균뿐 아니라 최악 시즌, 구간 회귀, bootstrap 하한과 두 모델의 오차
다양성을 함께 검사했다.

여섯 학습 작업은 모두 끝났지만 두 후보는 탈락했다. XGBoost는 보정 비중 5%에서
weighted gain `0.0000058661`, LightGBM은 10%에서 `0.0000125015`였다. 둘 다
양수였지만 사전에 정한 최소 개선량 `0.00005`보다 작았다. 2022→2023에서는 두
후보가 모두 나빠졌고, 기존 오차와의 상관도 각각 `0.9985597`, `0.9987254`로 허용
상한 `0.995`를 넘었다.

쉽게 말하면 모델 이름은 달랐지만 E2가 틀리는 곳에서 거의 같은 방식으로 틀렸다.
아주 작은 평균 개선만으로 복잡도를 늘릴 이유가 없어 제출 후보로 보내지 않았다.
이 판정은 XGBoost와 LightGBM 전체가 쓸모없다는 뜻이 아니다. 현재 피처와 E2 확률을
직접 고치는 고정 구조만 닫았다. 자세한 판정은
[S3 rejection](../reports/rejections/tree_hetero_residual_s3_rejection.json)에 남겼다.

## 9. 마지막 E3: 모델 가설보다 실행 예산이 먼저 무너졌다

마지막 후보는 이전보다 훨씬 공격적으로 설계했다. E2 확률을 안전한 anchor로 두고,
전체·최근·정규 시즌·특수 경기의 성공 전문가와 `middle`, `wild`, `reverse` 실패
전문가를 깊은 CatBoost로 학습한 뒤 작은 gate가 행마다 조합하도록 했다. 과거 감사에서
문제로 봤던 `middle`과 `reverse`의 중첩도 실제 현상이 함께 나타나는 정보로 다시
정의했다.

하지만 이 실험은 성능 판정까지 가지 못했다. 계획한 OOF 작업 63개 중 screening 14개,
confirmation 7개, extra seed 32개 등 총 53개를 완료한 뒤 Kaggle Version 70이
`33,677.4초`, 약 9시간 21분 시점에 메모리 부족으로 종료됐다. 남은 10개 OOF 작업뿐
아니라 최종 decision, 전체 학습, 행 독립성 감사도 실행되지 않았다.

따라서 이 결과를 “모델이 나빴다”는 기각으로 기록하지 않았다. 반대로 일부 학습 손실이
좋아 보인다는 이유로 성능 후보로 인정하지도 않았다. 판정은 `failed`이며, 부분 metric은
오직 진단 자료다. 실제 실행 소스 47개는 결과 ZIP과 바이트 단위로 대조해 저장소에
복구했고, 대용량 모델과 ZIP은 Git에 넣지 않고 해시만 남겼다.

가장 큰 교훈은 공격적인 모델과 무계획한 장시간 실행이 같은 말이 아니라는 점이다.
다음 대회에서는 대표 작업 하나의 시간과 peak RAM을 먼저 재고, 그 값으로 전체 작업 수와
동시 실행 수를 계산한다. 실행 제한의 70~80% 안에 끝나지 않으면 작업 수나 메모리 수명을
줄인 뒤 시작하며, 단계 사이 모델 풀을 해제하고 최신 resume 하나만 보존한다. 자세한
실패 근거는 [E3 failure evidence](../reports/evidence/failure_regime_e3_20260902.json)에
남겼다.

## 규칙을 연구 과정에 넣은 방법

이 대회에서는 평가 데이터의 각 행을 독립적으로 예측해야 한다. 그래서 다음 항목을
모델 성능과 별도의 합격 조건으로 뒀다.

- 평가 행 전체에서 평균, 빈도, 순위나 누적 통계를 계산하지 않는다.
- 현재 행의 투수·타자·상황만 학습 자료에서 미리 만든 상태에 조회한다.
- 평가 행 순서와 배치 크기를 바꿔도 같은 확률이 나와야 한다.
- 모델과 전처리의 해시가 검증 때와 다르면 제출 패키지를 만들지 않는다.
- Public 점수를 본 뒤 가중치나 보정 강도를 고르지 않는다.

규칙 위반 가능성이 있는 XGBoost 보정은 점수가 있어도 격리했고, review-only 실험은
검증을 통과하기 전까지 제출 ZIP을 만들지 않았다.

## 사용자와 AI는 어떻게 협업했나

사용자는 실험의 범위와 우선순위를 승인하고, Kaggle·Colab에서 전체 데이터와 GPU가
필요한 작업을 직접 실행했다. 로그와 결과 ZIP을 공유해 이상 여부를 함께 확인했고,
최종 제출 여부도 사용자가 결정했다.

AI는 실행 코드, 중단 후 재개할 수 있는 handoff 구조, manifest와 SHA-256 검사,
행 독립성 테스트와 문서 정리를 보조했다. 아이디어가 나올 때마다 바로 채택하지 않고
실험 계약과 합격 기준을 코드에 고정하는 역할도 맡았다. 이 저장소의 결과는 AI가
대신 돌린 자동 실험이 아니라, 사용자가 실행하고 확인한 증거를 함께 구조화한 기록이다.

## 지금까지의 결론

1. 이 데이터에서는 전처리를 많이 쌓는 것보다 검증된 한두 개의 상호작용이 나았다.
2. TabM은 유효했지만 더 긴 학습과 단순 seed 평균이 다음 개선으로 이어지지는 않았다.
3. 가장 큰 확인된 개선은 E2의 anchor residual CatBoost에서 나왔다.
4. OOF 개선은 배포 조건까지 재현돼야 제출 가치가 있다.
5. 실패한 실험은 숨길 결과가 아니라 다음 탐색 범위를 줄인 근거다.
6. 현재 최고 Public은 `977.3809532715`이며, S3는 실행을 마쳤지만 두 후보 모두
   최소 개선량과 오차 다양성 기준을 넘지 못했다.
7. E3는 깊고 다양한 전문가를 넣었지만 OOF 53/63에서 메모리 부족으로 실패했다.
   완료되지 않은 실행의 부분 metric으로 성능을 주장하거나 제출물을 만들지 않는다.
8. 다음 실험은 모델 아이디어와 함께 대표 작업의 시간·peak RAM을 먼저 측정하고,
   실행 제한 안에 decision과 audit까지 끝나는지 계산한 뒤 시작한다.
