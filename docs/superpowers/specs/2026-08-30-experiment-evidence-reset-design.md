# 실험 증거 장부 재정비 설계

## 목적

지금까지 완료한 실험을 같은 기준으로 다시 정리해, 이름만 다른 비슷한 후보를 반복하지
않고 다음 Kaggle GPU 예산을 점수 상승 가능성이 큰 한 번의 캠페인에 집중한다. 이번
단계는 새 모델을 학습하는 작업이 아니다. 기존 증거의 신뢰도와 비교 가능성을 먼저
확정하고, 그 결과로 다음 모델 캠페인의 범위와 중단 조건을 결정한다.

## 현재 문제

현재 `reports/EXPERIMENT_LEDGER.md`에는 초기 기준선부터 이종 트리 S3까지 23개 실험이
기록돼 있다. 이후에 실행한 Temporal T1/T2, R/F 전문가, S4
anchor-residual-hierarchical, TrackMan·profile 후보의 최종 판정과 반복 실패 원인은
장부에 충분히 반영되지 않았다.

검증 안전장치는 약한 후보를 제출하지 않는 역할을 했지만, 현재 기록만으로는 다음을
한눈에 판단할 수 없다.

- 어떤 후보가 실제 학습까지 완료됐고 어떤 후보가 실행 오류로 끝났는가
- 어느 결과가 원본 산출물로 검증됐고 어느 결과가 로그에만 남아 있는가
- 서로 비교 가능한 시간 전이 OOF를 사용했는가
- 개선량이 작은 이유가 모델 용량, 입력 신호, 특정 시즌 또는 배포 정렬 중 무엇인가
- E2와 다른 오차를 만든 후보가 실제로 있었는가
- 실제 Public 점수와 오프라인 판정이 어느 정도 같은 방향이었는가

## 검토한 접근법과 결정

### 접근법 A: 문서만 수동 갱신

가장 빠르지만 숫자 전사 오류를 자동으로 찾기 어렵고, 이후 실험이 추가될 때 같은
누락이 반복될 수 있다.

### 접근법 B: 가벼운 검증 장부

기계 판독 가능한 작은 JSON 장부와 사람이 읽는 감사 보고서를 함께 둔다. 범용 ZIP
수집 플랫폼은 만들지 않고, 확인된 실험만 명시적으로 등록한다. 이 방식을 채택한다.

### 접근법 C: 모든 과거 ZIP 자동 수집기

서로 다른 번들 스키마를 자동 추론할 수 있지만, 구현과 복구 비용이 크고 현재의
실험 속도 문제를 악화시킨다. 채택하지 않는다.

## 핵심 원칙

### 1. 증거와 해석을 분리한다

원본 수치, 출처, 해시와 검증 프로토콜은 장부에 기록한다. “왜 실패했는가”와 “다음에
무엇을 할 것인가”는 별도의 감사 보고서에서 해석한다. 해석이 바뀌어도 원본 수치는
바뀌지 않아야 한다.

### 2. 비교 가능한 결과만 비교한다

검증 fold, 행 집합, anchor와 가중 방식이 다른 Brier는 하나의 순위로 정렬하지 않는다.
비교 집합은 `comparison_group`으로 명시한다. Public 점수는 실제 제출이 확인된 경우만
기록하며 OOF 점수와 같은 척도처럼 회귀식을 맞추지 않는다.

### 3. 실패와 기각을 구분한다

- `failed`: 입력, 의존성, GPU, resume 또는 코드 오류로 성능 판단을 완료하지 못함
- `rejected`: 실행은 정상 완료됐으나 사전 성능 기준을 통과하지 못함
- `accepted`: 성능·안정성·규칙 gate를 모두 통과함
- `public_scored`: 실제 제출의 Public 점수가 확인됨. 현재 규칙 재검토에서 격리된
  역사 제출도 성과와 교훈을 보존하기 위해 이 상태를 사용할 수 있음
- `diagnostic`: 모델 후보가 아니라 가설의 적격성을 확인한 감사

오류가 난 뒤 복구 실행이 완료됐다면 오류와 최종 판정을 모두 이력으로 남기되, 실험의
최종 상태는 완료된 증거를 기준으로 정한다.

### 4. 출처 신뢰도를 표시한다

- `A`: 원본 review·handoff·delivery 번들을 현재 코드로 검증함
- `B`: 저장소에 커밋된 acceptance·rejection evidence 또는 해시가 있음
- `C`: 사용자가 전달한 실행 로그나 대화 기록만 있음

`C` 등급의 숫자는 다음 후보의 참고 자료로 쓸 수 있지만, 승인이나 제출 패키징의 단독
근거로 사용할 수 없다.

### 5. 규칙 준수와 성능을 별도 gate로 둔다

평가 행 간 평균·빈도·순위·누적값을 쓰지 않는 현재 행 독립성 원칙은 유지한다. 성능이
좋더라도 규칙 또는 데이터 계보가 불명확하면 제출 후보로 승격하지 않는다. 반대로 한
후보가 규칙이나 성능 gate에서 탈락해도 독립적인 다른 후보까지 막지는 않는다.

## 장부 구조

새 기계 판독 장부는 `reports/experiment_registry.json`에 둔다. 각 실험은 다음 필드를
갖는다.

- `experiment_id`, `family`, `variant`, `completed_at`
- `status`, `status_reason`, `evidence_grade`
- `comparison_group`, `folds`, `validation_rows`
- `baseline_id`, `baseline_brier`, `candidate_brier`
- `weighted_gain`, `worst_fold_gain`, `latest_fold_gain`
- `max_segment_regression`, `residual_correlation`, `seed_stability`
- `public_score`, `submission_sha256`
- `artifact_paths`, `artifact_sha256`, `evidence_paths`
- `rule_audit_status`, `row_independence_status`
- `failure_class`, `lesson`, `repeat_policy`

값을 확인할 수 없는 필드는 추정하지 않고 `null`로 둔다. 숫자의 단위와 방향은 필드
정의에 고정한다. `weighted_gain`과 fold gain은 양수일수록 개선이며 Brier는 낮을수록
좋다.

## 감사 산출물

### `reports/EXPERIMENT_LEDGER.md`

기존 표를 유지하되 최근 완료 실험을 추가한다. 비전문가도 이해할 수 있도록 각 결과에
한 문장 해석을 붙이고, 실행 오류와 성능 기각을 혼동하지 않게 표시한다.

### `reports/EXPERIMENT_RESET_AUDIT.md`

다음 내용을 한 번에 보여 준다.

1. 실제 Public 점수의 변화
2. 같은 OOF 프로토콜 안에서 확인된 개선량
3. 반복적으로 약했던 fold와 segment
4. E2 오차와 상관이 지나치게 높았던 후보
5. 닫을 계열, 다시 정의할 계열, 다음에 유지할 구성요소
6. GPU 시간을 쓰기 전에 확인해야 할 적격성 검사
7. 다음 단일 캠페인의 가설과 예상 GPU 예산

### `reports/experiment_registry.schema.json`

필수 필드, 허용 상태, 수치 범위와 `null` 정책을 고정한다. 장부가 문서와 다르게
편집되거나 부호가 뒤집히면 검사가 실패해야 한다.

## 다음 모델 캠페인의 깊이 기준

이번 감사 이후의 주력 후보는 작은 후처리나 단일 feature 추가 실험이 아니다. 다만
“깊은 모델”을 단순히 CatBoost `depth`나 신경망 층 수를 크게 만드는 것으로 정의하지
않는다. 고득점에 필요한 깊이는 입력 표현, 전문가 분기, 모델 용량과 앙상블 다양성을
함께 확보하는 구조적 깊이다.

다음 캠페인은 감사 결과가 뒷받침할 때 아래 축을 한 실행 안에서 단계적으로 비교한다.

- 시즌별 선수·상황 snapshot과 시간 감쇠 anchor
- 정규 시즌 `R`과 `F` 경기 유형의 전문가 분기
- 공식 학습 데이터로 안정적으로 정의 가능한 상황·오류 전문가
- 충분한 용량의 CatBoost 다중 seed
- CatBoost와 다른 오차가 확인된 경우에만 XGBoost·LightGBM residual 구성
- 구조 fold에서 고정한 residual correction 강도
- 마지막 단계의 계층 calibration

용량 후보는 얕은 기준선 하나와 공격적인 후보 여러 개를 함께 둔다. 예를 들어 트리
깊이, leaf 수, 반복 수와 정규화를 공동 탐색하되, 깊이만 키워 과적합한 모델을 좋은
모델로 간주하지 않는다. 최신 fold 하나만 좋아지는 후보도 승격하지 않는다.

1130점 외부 사례는 구조적 가설을 세우는 참고 자료로만 사용한다. 외부 모델 파일,
학습 통계 또는 출처가 증명되지 않은 상태를 우리 제출에 가져오지 않는다.

## 실행 흐름

1. 저장소 evidence와 현재 접근 가능한 결과 번들의 목록을 고정한다.
2. 각 번들의 무결성과 내부 manifest를 읽기 전용으로 검사한다.
3. 검증된 숫자를 registry에 명시적으로 등록한다.
4. schema 검사와 중복 ID·해시 검사를 실행한다.
5. registry와 Markdown 장부의 핵심 상태·Public 점수가 일치하는지 검사한다.
6. 비교 가능한 집합별로 성능, 안정성, 다양성과 실패 원인을 요약한다.
7. 감사 보고서에서 다음 캠페인의 필수 구성과 제외 구성을 결정한다.

## 오류 처리

- 존재하지 않는 과거 ZIP은 만들어 내거나 비슷한 파일로 대체하지 않는다.
- 같은 이름의 다운로드가 여러 개면 해시로 구분하고, 어떤 파일을 채택했는지 기록한다.
- 번들의 선언 해시와 실제 파일이 다르면 해당 증거를 등록하지 않는다.
- 프로토콜이 불명확하면 독립 `comparison_group`에 두고 직접 순위를 만들지 않는다.
- Public 점수를 확인할 수 없으면 빈 값으로 남긴다.
- 기존 사용자의 미커밋 파일은 수정하거나 포함하지 않는다.

## 검증

작은 fixture만 사용해 다음을 검사한다.

- 허용되지 않은 상태와 evidence 등급 거부
- Brier와 gain 범위 검사
- 중복 experiment ID와 서로 다른 해시 충돌 거부
- `public_scored`인데 Public 점수가 없는 레코드 거부
- evidence 등급 `A` 또는 `B`의 신규 `public_scored` 레코드에 제출 해시가 없으면
  거부하되, 해시를 보존하지 못한 역사 제출은 등급 `C`와 사유를 명시해 기록
- `accepted`인데 규칙 감사가 실패한 레코드 거부
- 비교 그룹이 다른 Brier를 하나의 순위로 합치지 않음
- JSON 장부와 Markdown 요약의 실험 수·상태·Public 점수 일치

전체 데이터 학습, GPU 실행, 패키지 설치와 제출 ZIP 생성은 이 검증에 포함하지 않는다.

## 완료 조건

- 확인 가능한 완료 실험이 중복 없이 registry에 기록된다.
- 기존 장부의 Public 점수와 registry가 일치한다.
- 최근 누락 실험의 최종 상태와 증거 등급이 기록된다.
- 반복할 가치가 없는 가설과 아직 열어 둘 가설이 구분된다.
- 다음 캠페인이 작은 보정의 나열이 아니라 구조적으로 깊은 단일 캠페인으로 정의된다.
- 다음 캠페인의 GPU 실행 시간, 중간 중단 기준과 제출 승격 조건을 실행 전에 고정할 수
  있다.

## 범위 밖

- 이번 단계에서 새 모델 학습
- 모든 과거 번들 형식을 자동 인식하는 범용 수집기
- Public 점수로 사후 가중치 최적화
- 자동 DACON 제출
- acceptance 없이 제출 ZIP 생성
