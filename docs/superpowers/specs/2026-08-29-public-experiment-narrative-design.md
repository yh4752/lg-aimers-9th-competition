# 공개 실험 여정 문서화 설계

## 목적

이 저장소의 전처리 연구부터 현재 이종 트리 잔차 실험까지를 하나의 의사결정 흐름으로 정리한다. 팀원은 실험을 재개할 수 있어야 하고, 인공지능을 잘 모르는 채용 담당자나 평가자도 무엇을 고민하고 어떻게 개선했는지 이해할 수 있어야 한다.

문서는 모델 이름을 나열하는 대신 다음 질문에 답한다.

1. 어떤 문제를 발견했는가?
2. 왜 그 실험을 선택했는가?
3. 무엇을 어떻게 검증했는가?
4. 결과가 어땠고 무엇을 채택하거나 폐기했는가?
5. 그 판단이 다음 실험으로 어떻게 이어졌는가?

## 독자와 문서 계층

### 1. `README.md`: 외부 독자를 위한 입구

README는 2분 안에 전체 프로젝트를 파악할 수 있는 공개 요약이다.

- 확률 예측 문제를 쉬운 말로 설명한다.
- 로컬 검증과 Public 점수가 다른 이유를 설명한다.
- 대표 점수 변화와 중요한 방향 전환을 짧은 타임라인으로 보여준다.
- 최신 상태와 다음 실험을 명확히 적는다.
- 상세한 근거는 실험 여정과 장부로 연결한다.

README에는 모든 후보와 파라미터를 넣지 않는다. 결과보다 의사결정 능력, 검증 원칙, 규칙 준수, 실패에서 배운 점이 먼저 보이게 한다.

### 2. `docs/EXPERIMENT_JOURNEY.md`: 상세한 연구 이야기

팀원과 미래의 작성자가 실험의 맥락을 복원하는 문서다. 각 단계는 아래 형식을 따른다.

```text
문제 인식 → 가설 → 실험 설계 → 확인된 결과 → 판단 → 다음 단계
```

다룰 범위는 다음과 같다.

1. 시간 순서 검증 기반과 초기 기준선
2. FwFM, 초기 calibration, XGBoost 탐색
3. EDA와 Stage 1~5 전처리 연구
4. TabM 선택, 첫 제출과 seed·행 단위 파생변수 실험
5. CatBoost·TabM 혼합과 OOF 정렬 재검증
6. 시간 가중 포트폴리오와 계층 보정 실험
7. CatBoost 전문가 E1/E2와 Public 977점
8. T3, R/F 전문가, 실패 유형 라벨 감사와 폐기 판단
9. 현재 XGBoost·LightGBM 잔차 보정 S3

실행이 끝나지 않은 후보는 결과처럼 쓰지 않고 `진행 중` 또는 `미실행`으로 표시한다. 실패한 실험은 숨기지 않되, 실패가 줄인 탐색 범위와 다음 판단에 준 정보를 함께 적는다.

### 3. `reports/EXPERIMENT_LEDGER.md`: 수치의 단일 기준

장부는 서술 문서가 인용하는 사실의 원본이다.

- 실험 ID, 모델 계열, 검증 프로토콜, 핵심 수치, 판정, Public 점수, 근거를 기록한다.
- 서로 다른 검증 프로토콜의 Brier를 직접 순위화하지 않는다.
- 실제 제출하지 않은 후보에는 Public 점수를 쓰지 않는다.
- 대용량 ZIP과 모델 대신 논리 실행 ID, 작은 evidence 경로와 SHA-256을 남긴다.
- 수치가 확인되지 않은 실행은 장부에 새 결과 행으로 추가하지 않는다.

`docs/rounds/README.md`는 실험 여정과 기존 라운드 문서를 연결하는 색인으로 갱신한다.

## 비전문가를 위한 설명 원칙

전문 용어는 처음 등장할 때 다음 순서로 설명한다.

1. 일상적인 의미 또는 비유
2. 정확한 기술 정의
3. 이 프로젝트에서 왜 필요했는지

예시는 다음과 같다.

- **Brier Score**: 확률 예측이 정답에서 얼마나 멀리 벗어났는지 제곱해 평균낸 값이며 낮을수록 좋다.
- **시간 전이 검증**: 과거 시즌으로 공부한 뒤 미래 시즌을 맞혀 보는 모의고사다.
- **OOF 예측**: 해당 행의 정답을 학습에 보지 않은 모델이 만든 검증 예측이다.
- **Anchor**: 새 모델이 처음부터 모든 것을 다시 맞히지 않도록 기준이 되는 기존 확률이다.
- **Residual correction**: 기존 확률의 실수 중 반복되는 부분만 작은 폭으로 고치는 방식이다.
- **앙상블**: 서로 다른 모델의 판단을 합쳐 한 모델의 편향을 줄이는 방법이다.

본문은 쉬운 설명만으로도 흐름을 이해할 수 있게 쓰고, 정확한 파라미터와 수치는 접기 기능 대신 연결된 설계·장부 문서에서 확인하게 한다.

## 포트폴리오 관점

문서는 단순히 높은 점수를 주장하지 않는다. 다음 역량이 근거와 함께 드러나게 한다.

- 미래 정보를 보지 않는 시간 순서 검증 설계
- 대회 규칙을 코드와 산출물 gate로 강제한 과정
- 실패한 모델 계열을 근거 없이 반복하지 않고 범위를 줄인 판단
- GPU 시간과 중단 위험을 고려한 resume·handoff 설계
- Public 점수보다 재현 가능한 OOF evidence를 우선한 선택
- AI가 코드 작성과 검증 자동화를 도왔고, 사용자가 실행·결과 전달·최종 판단을 담당한 협업 구조

개인 기여는 실제 기록으로 확인되는 범위에서만 쓴다. 다른 참가자의 1130점 제출물은 복제 성과로 표현하지 않고, 구조를 비교해 새로운 가설을 얻은 외부 사례로만 설명한다.

## 사실 확인과 출처

작성 전에 기존 장부, acceptance/rejection JSON, 라운드 문서, 실행 안내, 현재 Git 커밋을 대조해 사실 표를 만든다. 우선순위는 다음과 같다.

1. 실제 Public 제출 점수와 acceptance/rejection evidence
2. 검증된 review/handoff manifest와 해시
3. `reports/EXPERIMENT_LEDGER.md`
4. 설계·구현 문서
5. 대화 기록이나 계획 문서

상위 근거와 충돌하는 계획 문서는 과거 의도로만 취급한다. 결과 ZIP을 읽지 못하거나 수치를 재확인할 수 없으면 정성적 흐름만 기록하고 수치는 쓰지 않는다.

## GitHub 반영 범위

- 문서와 이미 커밋된 재현 코드를 `main`에 push한다.
- 원본 데이터, 모델, OOF 전체 파일, review/resume/handoff ZIP은 push하지 않는다.
- 현재 main의 미커밋 TabM 복구 코드와 Notebook은 이번 문서 커밋에 포함하지 않는다.
- 토큰, 로컬 절대 경로, 개인 식별 정보가 새 문서에 들어가지 않도록 검사한다.
- push 직전에 원격 `main`을 다시 조회하고 비선형 변경이 있으면 중단한다.

## 검증 기준

완료 전 다음을 확인한다.

- README, 실험 여정, 장부 사이의 상태와 점수가 일치한다.
- 모든 내부 링크가 실제 파일을 가리킨다.
- `TBD`, `TODO`, 근거 없는 최상급 표현과 미확인 수치가 없다.
- Markdown 표와 제목 구조가 정상이다.
- 새 문서만 별도 커밋되며 기존 미커밋 작업은 유지된다.
- push 후 `origin/main`과 로컬 `main`이 같은 커밋을 가리킨다.

## 완료 산출물

1. 비전문가와 포트폴리오 독자를 위한 최신 `README.md`
2. 전체 의사결정 흐름을 담은 `docs/EXPERIMENT_JOURNEY.md`
3. 확인된 최신 실험을 반영한 `reports/EXPERIMENT_LEDGER.md`
4. 실험 문서 색인을 갱신한 `docs/rounds/README.md`
5. 위 문서와 기존 커밋이 반영된 GitHub `main`
