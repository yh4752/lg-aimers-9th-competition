# LG Aimers 포트폴리오 마무리 설계

## 목적

대회 저장소를 공개하거나 포트폴리오에서 연결해도 개인정보·대회 원본·실험 산출물이
노출되지 않게 점검하고, 비전공자도 프로젝트의 판단 흐름과 작성자의 역할을 이해할 수
있는 진입점을 만든다.

## 사실 기준

- 최고 확인 제출 점수는 `977.3809532715`다.
- Tree Expert E2의 기준 확률은 과거 학습 데이터에서 만든 투수 성공률이며, TabM은
  비교 기준이다.
- E3는 약 `33,677초` 실행 후 메모리 부족으로 종료됐다. 성능 기각이 아니라 실행
  실패다.
- 전체 데이터 학습과 제출 실행은 사용자가 맡았고, Codex는 코드 작성·검토와 결과
  분석을 보조했다.
- 검증 방식이 다른 점수는 직접 순위로 비교하지 않는다.

## 변경 범위

### 1. 공개 저장소 점검과 경로 정리

현재 파일과 Git 이력에서 비밀키·토큰, 대용량 데이터·모델 파일을 검사한다. 문서에
남은 `/Users/yonghyun/...` 경로는 `<REPO_ROOT>`, `<DOWNLOAD_DIR>`처럼 누구나 바꿔
쓸 수 있는 표기로 정리한다. 과거 실행 기록의 의미는 바꾸지 않으며, 경로 금지 여부를
검사하는 테스트 문자열은 그대로 둔다.

### 2. 대표 그림

`docs/assets/lg-aimers-experiment-journey.svg` 한 장으로 다음 흐름을 보여 준다.

```text
시간 전이 검증 → 전처리 연구 → TabM 872.39 → Tree Expert E2 977.38
                                                ↘ E3: OOM, 성능 미판정
```

그림은 외부 폰트나 스크립트 없이 GitHub에서 바로 보이는 정적 SVG로 만든다. README의
초반부에 연결하고, 색상만으로 상태를 구분하지 않도록 텍스트 표기를 함께 둔다.

### 3. 포트폴리오 요약

`docs/PORTFOLIO_SUMMARY.md`는 문제, 제약, 검증 설계, 핵심 실험, 성과, 실패에서 배운
점, 역할 분담, 코드·증빙 링크 순서로 작성한다. 채용 담당자가 1~2분 안에 읽을 수 있는
분량을 목표로 하며 확인되지 않은 성과는 넣지 않는다.

### 4. 면접 문답

`docs/INTERVIEW_QA.md`에는 비전공자 질문과 기술 질문을 함께 둔다. 각 답변은 결론,
근거, 한계 순서로 짧게 작성하고, 실제로 사용자가 이해하고 설명할 수 있는 내용만
포함한다. OOF, Brier 점수, anchor, 잔차 보정은 처음 등장할 때 뜻을 설명한다.

## 검증

- 추적 파일과 Git 이력의 대표 비밀정보 패턴 재검사
- 추적된 데이터·모델·ZIP 및 5MB 초과 파일 부재 확인
- 개인 로컬 경로는 허용된 테스트 문자열 외에 남지 않았는지 확인
- Markdown 링크와 SVG XML 구문 확인
- 최고 점수, E3 실행 시간·상태, 역할 분담 문구를 원본 장부와 대조
- 관련 문서 테스트와 전체 테스트 실행

## 제외 범위

- 저장소 공개 전환
- 데이터·모델·제출 ZIP 추가 또는 재생성
- 새 전처리·학습·추론 실행
- Git 과거 이력 재작성
- 사용자 소유의 미추적 파일 변경
