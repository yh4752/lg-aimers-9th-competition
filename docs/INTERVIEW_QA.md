# LG Aimers 9기 면접 문답

이 문서는 답을 외우기 위한 대본보다, 프로젝트를 내 말로 설명하기 위한 복습 자료다.
직접 하지 않은 일을 구현했다고 말하지 않고, 확인한 결과와 도움받은 부분을 구분한다.

## 프로젝트를 한 문장으로 설명한다면?

야구 투구 직전의 정보로 제구 성공 확률을 예측하면서, 시간 순서를 지킨 검증과 평가 행
독립성을 기준으로 전처리와 모델을 비교한 프로젝트다. 최고 확인 Public 점수는
`977.3809532715`였다.

## 왜 무작위 분할을 쓰지 않았나?

실제 상황에서는 과거 기록으로 미래 시즌을 예측해야 하기 때문이다. 데이터를 무작위로
섞으면 미래 시즌의 패턴이 학습 데이터에 들어가 검증이 쉬워질 수 있다. 그래서
2021→2022, 2022→2023, 2023→2024 순서로 학습 구간과 검증 구간을 나눴다.

## OOF가 무엇인가?

OOF는 **Out-of-Fold 예측**의 줄임말이다. 어떤 행의 정답을 학습에 사용하지 않은 모델이
그 행을 예측한 값이다. 이 프로젝트에서는 시간 구간별 OOF를 모아 전처리와 모델을 같은
조건에서 비교하고, 혼합 비율이나 후보 채택 여부를 정했다.

## Brier 점수는 무엇인가?

예측 확률과 실제 결과의 차이를 제곱해 평균한 값이다. 실제 정답이 `1`일 때 `0.9`를
예측하면 오차는 작고 `0.1`을 예측하면 크다. 로컬 Brier는 낮을수록 좋다. DACON
Public 점수는 대회가 별도로 환산한 점수라 높을수록 좋으며, 두 숫자를 같은 척도로
해석하지 않았다.

## `comparison_group`은 왜 필요했나?

검증 행과 계산 방식이 같은 결과끼리만 비교하기 위해서다. 2023→2024 한 구간만 본
실험과 세 시즌을 합친 OOF는 난이도와 행 구성이 다르다. 같은 그룹 안에서는 수치를 직접
비교할 수 있지만, 다른 그룹의 Brier를 한 줄로 세워 모델 순위를 만들지는 않았다.

## 평균 성능이 좋아도 최악 구간을 본 이유는?

평균 개선이 한 시즌의 큰 이득에서만 나왔다면 다음 시즌에도 안정적이라고 보기 어렵기
때문이다. 세 시간 구간의 방향이 같은지와 가장 약한 구간의 개선량을 함께 봤다. 이 기준
때문에 평균은 좋아도 특정 구간이 나빠진 후보를 제출하지 않았다.

## anchor와 잔차 보정은 무엇인가?

Anchor는 모델이 출발하는 기준 확률이다. E2에서는 과거 학습 데이터의 투수 통산·시즌·
최근 성공률을 사용하되, 기록이 적은 선수의 값은 전체 평균 쪽으로 조정했다. CatBoost는
정답 전체가 아니라 `실제 결과 - anchor`에 해당하는 남은 오차를 학습했다. 이것이 잔차
보정이다.

## E2의 anchor가 TabM 예측이었나?

아니다. E2의 anchor는 과거 투수 기록으로 만든 확률이다. TabM은 E2가 실제로 더 나은지
판단하기 위한 비교 기준이었다. 이 둘을 혼동하면 모델 구조를 잘못 설명하게 된다.

## TabM에서 Tree Expert E2로 바꾼 이유는?

TabM은 규칙을 지킨 첫 딥러닝 기준선으로 Public `872.3920184667`을 기록했지만, 더 오래
학습하거나 seed만 늘리는 방식은 OOF에서 이득이 없었다. E2는 범주형 상호작용에 강한
CatBoost와 투수 기반 anchor를 결합해 다른 가설을 시험했고, 세 시간 구간 모두에서
개선된 뒤 Public `977.3809532715`를 기록했다.

## 왜 모델 세 개를 평균했나?

학습 난수에 따른 흔들림을 줄이기 위해서다. 다만 seed를 늘리면 항상 좋아지는 것은
아니다. E2의 세 seed 평균은 사전 검증을 통과했지만, TabM seed 평균은 단일 seed보다
나빠 기각했다. 모델 수보다 실제 OOF 개선 여부를 기준으로 삼았다.

## 대회 규칙은 어떻게 지켰나?

평가 행 하나를 예측할 때 다른 평가 행의 평균, 빈도, 순위나 누적값을 사용하지 않았다.
학습 데이터에서 고정한 전처리와 통계만 현재 행에 적용했다. 행 순서를 뒤집거나 섞고,
배치 크기를 바꾸고, 한 행만 넣어도 예측이 같은지 검사했다. 패키징은 acceptance와 파일
해시가 맞는 후보에만 허용했다.

## E3는 성능이 나빠서 실패했나?

그렇게 판단할 수 없다. E3는 OOF 작업 63개 중 53개를 끝낸 뒤 약 `33,677초` 시점에
메모리 부족으로 종료됐다. 최종 의사결정 단계에 도달하지 못했으므로 성능 기각이 아니라
실행 실패다. 부분 지표를 근거로 좋거나 나쁜 모델이라고 말하지 않았다.

## 이 프로젝트에서 직접 맡은 부분은?

실험 방향을 확인하고 Kaggle·Colab의 전체 학습을 실행했으며, 로그와 결과 파일을 다음
검토에 전달했다. 후보 진행·중단과 실제 제출을 결정하고 Public 점수를 확인했다. Codex는
코드 작성, 정적 검사, 규칙 점검과 결과 분석을 보조했다. 전체 구현을 혼자 했다고
표현하지 않는 것이 이 프로젝트를 정확히 설명하는 방법이다.

## 가장 아쉬운 점은?

E3처럼 큰 실험을 시작하기 전에 전체 작업 수와 최대 메모리를 충분히 실측하지 못한
점이다. 실행 후반까지 갔지만 최종 판단과 제출 가능성 검사에 도달하지 못했다. 긴 실행
자체보다, 중간에 자원을 회수하고 최신 복구 파일 하나만 남기는 운영 설계가 부족했다.

## 다시 한다면 무엇을 먼저 바꿀 것인가?

가장 큰 작업 하나를 먼저 실행해 시간과 최대 메모리를 잰다. 그 결과로 전체 작업 수와
동시 실행 수를 정하고, 전체 과정이 제한의 70~80% 안에 들어올 때만 장시간 실험을
시작한다. 모델 선택에서는 같은 시간 전이 OOF, 최악 구간, seed 편차와 행 독립성을
함께 확인한다.
